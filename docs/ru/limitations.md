# Проверка перед внедрением и ограничения

> English version: [limitations.md](../en/limitations.md). Обзор расширения - в [README](../../README.md).

## Что проверить до внедрения

**Важно:** `fasttruncate()` не является транзакционной заменой `TRUNCATE`.
После начала физической очистки `ROLLBACK` не восстановит прежние данные.

Перед использованием проверьте следующее:

1. Целевые таблицы являются самостоятельными локальными временными
   heap-таблицами, то есть используют стандартный метод хранения PostgreSQL.
   Это основной поддерживаемый сценарий.
2. Для секционирования и наследования не требуется обход дочерних отношений.
3. Для очистки не нужны внешние ключи, `CASCADE`, TRUNCATE-триггеры и
   `RESTART IDENTITY`.
4. В PostgreSQL включен `track_counts`:

   ```sql
   SHOW track_counts;
   ```

   Ожидаемое значение - `on`.

5. После каждого повторного заполнения код вызывает `fasttrun_analyze()`.
6. Опечатки в именах контролируются приложением: отсутствующая таблица для
   основных функций считается допустимым случаем и не вызывает ошибку.
7. Для каждого серверного соединения предусмотрен бюджет памяти. По умолчанию
   кеш статистики fasttrun не ограничен.
8. Для пулера определено, кто очищает временные таблицы перед их использованием
   следующим клиентом. Само расширение не знает о границах клиентов пулера.
9. У приложения есть возможность вернуться к обычным `TRUNCATE` и `ANALYZE`.
10. Право `EXECUTE` выдано только доверенным ролям. Функции работают с правами
    вызывающего пользователя, но не повторяют все проверки владения и ACL,
    которые выполняют штатные `TRUNCATE` и `ANALYZE`.

Не начинайте внедрение с учета и предварительного создания таблиц. Основные
функции работают без `shared_preload_libraries`.

## Ограничения

- Основной поддерживаемый контракт - самостоятельная локальная временная
  heap-таблица текущего backend.
- Секционированный родитель и родитель наследования отклоняются. Листовой
  раздел, который сам является heap-таблицей, или таблица-наследник без
  собственных потомков может быть принят, но fasttrun обработает только это
  отношение и не станет обходить иерархию.
- Внешние ключи не проверяются, `TRUNCATE ... CASCADE` не выполняется.
- `BEFORE TRUNCATE` и `AFTER TRUNCATE` триггеры не вызываются.
- `DELETE`-триггеры также не вызываются.
- Последовательности SERIAL/IDENTITY не сбрасываются.
- Физическая очистка не откатывается транзакцией.
- `fasttruncate()` публикует `reltuples=0`. Ядерный `TRUNCATE` использует
  служебное значение `-1`, поэтому после повторного заполнения особенно важно
  вызвать `fasttrun_analyze()`.
- Статистика наследования не собирается. Объекты `CREATE STATISTICS` fasttrun
  сам не строит: таблицу с такими объектами `fasttrun_analyze()` передает
  обычному `ANALYZE`, со всеми его записями в каталог и общими сообщениями
  инвалидации. Если объект удаляет каскад от другого объекта, например
  `DROP SCHEMA ... CASCADE` его схемы или `DROP TYPE ... CASCADE`, backend
  держит запись кеша таблицы до ее удаления или следующего `ANALYZE`: неверных
  оценок это не дает.
- Статистика выражений частичных индексов не собирается, а при
  `fasttrun.use_typanalyze = off` не собираются и выражения обычных индексов.
  Старая каталожная статистика таких выражений скрывается, и до обычного
  `ANALYZE` планировщик использует оценки по умолчанию.
- ACL, RLS и security-barrier поведение обычного `ANALYZE` не воспроизводится.
- Функции не проверяют владение таблицей и привилегии штатных `TRUNCATE` и
  `ANALYZE`. Доступ нужно ограничивать правом `EXECUTE`.
- Локальная статистика сохраняется между транзакциями одного backend, но
  исчезает при завершении соединения.
- Запись, которая идет мимо исполнителя и `COPY`, например прямая запись
  другого расширения через table AM, в журнал транзакции не попадает. Если в
  той же транзакции не было вызова `fasttrun_analyze()` для этой таблицы,
  `COMMIT` не переносит ее счетчики, и следующий вызов считает строки от
  прежней базы. Число строк остается старым, а статистику колонок скрывает
  только изменение размера таблицы втрое и больше. Вызов `fasttrun_analyze()`
  после заполнения в той же транзакции переносит и такую запись, поэтому
  вызывайте его после каждого заполнения. Очистку `ON COMMIT DELETE ROWS`
  fasttrun распознает по пустому хранилищу при следующем обращении к таблице.
- Локальные планы сбрасываются только в текущем backend. Во время работы
  `ResetPlanCache` не вызывается: он вызывается не более одного раза, при
  завершении backend, перед удалением временных таблиц ядром.
- Отсутствующая таблица для основных функций считается допустимым случаем:
  функция ничего не делает.
- Учет `UPDATE` по колонкам, однажды снятый с таблицы, возвращается только
  следующим пересбором: если триггер создали внутри savepoint и откатили его,
  учет для этой таблицы остается приостановленным.
- Запись мимо executor'а - прямой вызов heap/table AM API сторонним расширением -
  в список колонок не попадает. Пути ядра так с временными таблицами не работают.
- Реестр идущих пишущих операторов вмещает 16 пар "временная таблица,
  подтранзакция" одновременно, считая и вложенные операторы (триггеры,
  функции, modifying CTE). Корень секционированной временной таблицы тоже
  занимает место: `UPDATE` или `DELETE` без отсечения по 16 секциям дает 17
  целей, как и родитель наследования с 16 потомками. При переполнении до конца
  транзакции любая таблица считается записываемой: статистика, собранная в этой
  транзакции после такого оператора, не отдается планировщику, пока ее не
  заменит новый сбор. Постоянные таблицы в этот счет не входят.
- Для `INSERT` и `COPY` в секционированную временную таблицу реестр запоминает
  названного в операторе родителя, а секцию ядро выбирает позже, при
  маршрутизации строк. Сбор статистики самой секции изнутри такого оператора,
  например из триггера, не видит идущей записи и может отдать выборку, снятую
  во время нее. Первый проход по секции изнутри такого оператора считает строки
  по старому снимку, и это число переходит в следующие транзакции, пока
  `fasttruncate()` или `TRUNCATE` не очистит секцию. `UPDATE` при конфликте
  `INSERT ... ON CONFLICT` через родителя идет прямо в секцию, и учет
  измененных колонок секции его не видит.
- В сеансе без предзагрузки библиотеки первый вызов fasttrun внутри
  modifying CTE не видит внешнего оператора, и первый проход по таблице может
  сохранить число строк по старому снимку. Предзагрузка через
  `shared_preload_libraries` или `session_preload_libraries` это исключает.
- Функция, которая внутри пишущего оператора выключает `track_counts`
  (параметр суперпользователя), отключает подсчет у уже открытой таблицы, и
  такая запись не попадает в перенос счетчиков через `COMMIT`.
- Пересбор статистики колонок запускает только износ. Без нового DML или
  явного `fasttrun_collect_stats()` колонка остается на оценках по умолчанию
  в таких случаях: после явного сбора во время записи, если analyze вызван до
  `COMMIT`, и до конца транзакции после переполнения реестра пишущих
  операторов.
- Откат точки сохранения, внутри которой смена типа колонки или другой
  `ALTER TABLE`, кроме добавления колонки, переписал таблицу, прежнюю
  статистику колонок не возвращает: колонки остаются на оценках по умолчанию
  до следующего DML и analyze или явного `fasttrun_collect_stats()`. В корпусе
  OmniX временные таблицы переписывает только `ADD COLUMN ... GENERATED ...
  STORED` в `imp_readings_integral`, а его статистика сохраняется и
  возвращается откатом.
- fasttrun не является границей безопасности между клиентами пулера.
