# Статистика, настройки и память

> English version: [statistics.md](../en/statistics.md). Обзор расширения - в [README](../../README.md).

## Как обновляется статистика

### Размер таблицы

`fasttrun_analyze()` публикует в памяти текущего backend значения, которые
планировщик использует для оценки размера таблицы и индексов.

Повторный вызов вычисляет число строк по счетчикам изменений и не сканирует
таблицу, в том числе в следующих транзакциях: при `COMMIT` fasttrun переносит
счетчики завершенной транзакции, и записи, сделанные без вызовов fasttrun,
учитываются так же. Таблицу снова сканирует первый вызов в таких случаях:

- после ядерного `TRUNCATE` или смены файла таблицы
- после записи при выключенном `track_counts` и при недоступных счетчиках
- после прохода по таблице внутри оператора, который пишет эту таблицу: такой
  проход не видит строк, которые счетчики уже посчитали
- после `COMMIT`, который скрыл статистику колонки
- после `VACUUM`: он меняет число и видимость страниц мимо счетчиков
- после очистки `ON COMMIT DELETE ROWS`: первый вызов транзакции проверяет,
  не пусто ли хранилище

Дельта к числу строк, полученному выборкой блоков, тоже остается оценкой.

Планировщик делит опубликованное число строк на опубликованное число страниц и
умножает на фактическое число страниц. Откаченная запись оставляет свои страницы
в файле, а счетчики ее забывают. Откат подтранзакции или транзакции считает,
сколько страниц добавила именно его откаченная запись: рост файла от строк,
зафиксированных без analyze, к ним не относится, а вложенные откаты одного
роста не складываются. Эти страницы планировщик не учитывает в оценке, запасной
сигнал по размеру не принимает их за новое заполнение, а следующий analyze
измеряет размер заново и обновляет оценки индексов. После `VACUUM` число строк,
число страниц и видимость берутся у `VACUUM`: он только что посчитал их по
файлу. `VACUUM`, который ядро пропустило из-за прав или который не обрабатывал
кучу (`PROCESS_MAIN false`, `ONLY_DATABASE_STATS`), ничего не меняет. Повторенная
опция, как и в ядре, действует последним значением.

Если таблица не превышает `fasttrun.max_analyze_pages`, сканирование дает
точное число строк. Для более крупной таблицы используется ограниченная
выборка блоков и получается оценка, как при обычном `ANALYZE`. Пересбор
статистики после изменений и пересчет частичных индексов знают точное число
строк из счетчиков, если исходное число дал полный проход, и тогда берут
выборку блоков, а не читают всю таблицу. Таблицу не больше цели выборки они
читают полным проходом при любом `max_analyze_pages`, кроме нуля: выборка блоков
прочла бы ее всю и вдобавок взяла бы `ProcArrayLock`, обходя все процессы
сервера. Если исходное число было
оценкой, они ведут себя как первый проход и заменяют его тем, что измерили.
`max_analyze_pages=0` возвращает полный проход и для них. Зерно выборки
тоже берется как у `ANALYZE`, из генератора, который ядро засевает в каждом
процессе отдельно, поэтому backend выбирают блоки независимо друг от друга и
при `shared_preload_libraries`.

### Статистика столбцов

По умолчанию fasttrun использует тот же механизм анализа обычных столбцов, что
и PostgreSQL. Рассчитываются наиболее частые значения (MCV), гистограмма,
корреляция, доля NULL, средняя ширина и число различных значений.

Размер выборки по умолчанию - 3000 строк. Это компромисс между скоростью и
качеством. Обычный `ANALYZE` часто использует заметно большую выборку. Для
наиболее близкого поведения установите:

```sql
BEGIN;
SET LOCAL fasttrun.sample_rows = -1;
-- Заполнение, fasttrun_analyze() и рабочие запросы.
COMMIT;
```

Даже в этом режиме полное совпадение результатов не гарантируется: случайные
выборки могут различаться. Сбор будет дороже, чем с настройками по умолчанию.
`SET LOCAL` не оставляет измененные параметры следующему клиенту пулера.

Цель статистики колонки (`ALTER TABLE ... ALTER COLUMN ... SET STATISTICS`)
fasttrun учитывает так же, как `ANALYZE`: `0` выключает сбор колонки, а
значение больше нуля задает число MCV и корзин гистограммы. `CREATE TABLE ...
(LIKE шаблон)` эту настройку не копирует, а `ALTER TABLE` на каждой временной
таблице сам пишет каталог и рассылает общие сообщения инвалидации. Поэтому
колонка временной таблицы, у которой цель не задана, берет ее у одноименной
колонки одноименной таблицы в схеме `fasttrun.prewarm_schema`. Настройка
делается один раз на шаблоне:

```sql
ALTER TABLE dummy_tmp.my_table ALTER COLUMN payload SET STATISTICS 0;
```

Отключает это поведение `fasttrun.template_stattarget = off`.

`UPDATE` учитывается по колонкам. pgstat считает измененные строки по таблице
целиком, и при таком подсчете обновление одной служебной колонки обесценивало бы
статистику всех остальных. Поэтому износ от `UPDATE` относится только к
колонкам, названным в `SET`, а `INSERT` и `DELETE` - ко всем сразу.

Учет требует предзагрузки: цели оператора видны только при его старте, а хуки
ставятся при загрузке библиотеки.

```
session_preload_libraries = 'fasttrun'
```

Без предзагрузки учет по колонкам выключен целиком, износ от `UPDATE` относится
ко всем колонкам сразу, и один раз за сеанс об этом пишется в серверный лог.
Образец, снятый пока таблицу пишут, не отдается планировщику ни в одном из
режимов, пока его не заменит новый. Сравнивать его не с чем - выборка идет по
снимку своей команды, а счетчики рядом уже включают эти записи.

`session_preload_libraries` загружают только клиентские сеансы. Фоновые
воркеры - pg_background, pg_cron в режиме фоновых воркеров, задания
TimescaleDB - этот параметр не обрабатывают, и учет по колонкам в них включает
только `shared_preload_libraries`. Он требует рестарта PostgreSQL, и обновлять
библиотеку после перехода тоже придется с рестартом (раздел ["Обновление и удаление"](install.md#обновление-и-удаление)). Общий реестр учета `CREATE TEMP TABLE` при этом создается, но запись
в него по умолчанию выключена и включается параметром
`fasttrun.track_temp_creates` (раздел ["Учет и предварительное создание таблиц"](tracking.md)). Строку о выключенном
учете такие процессы пишут уровнем DEBUG1, а не LOG: иначе короткоживущие
воркеры писали бы тысячи одинаковых строк в сутки.

Для отдельной таблицы учет отключается до следующего пересбора, когда списку
колонок нельзя доверять: есть триггеры или stored generated column, `UPDATE`
пришел к наследнику через родителя, либо статистика колонки старше последнего
пересбора.

Список берется из целей оператора, а не из измененных значений: `UPDATE` без
единой совпавшей строки колонку все равно отметит, и дальше ей засчитывается
весь оборот таблицы за период.

Цена: массовый `UPDATE` портит физический порядок строк, поэтому у непритронутых
колонок корреляция может оказаться завышенной - индексный доступ для них
выглядит дешевле, чем есть. Число различных значений, доля NULL и MCV остаются
верными.

`fasttrun_analyze()` после любого DML с момента прошлого сбора пересобирает
статистику столбцов, как обычный `ANALYZE`, если автоматический сбор включен,
`sample_rows` не равен нулю и лимит памяти разрешает сбор. Старая выборка не
знает значений, которые принес DML: новая дата, флаг, взведенный у части строк,
или колонка, заполненная там, где были только NULL, получили бы оценку в одну
строку. Вызов без изменений выборку не трогает. Пересбор дороже дельты и
сбрасывает сохраненные планы таблицы, замер цены - в разделе
["Цена пересбора"](#цена-пересбора).

Вызов внутри оператора, который пишет эту таблицу, пересбор откладывает:
выборку, снятую во время записи, fasttrun планировщику не отдает. Следующий
вызов после окончания записи, в той же транзакции или после `COMMIT`, собирает
заново. Без нового износа колонка остается на оценках по умолчанию в нескольких
случаях, они перечислены в [ограничениях](limitations.md).

Между DML и следующим вызовом analyze планировщик пользуется собранной
статистикой в пределах допуска, как ядро между двумя запусками `ANALYZE`, а
сверх допуска fasttrun ее скрывает, чтобы планировщик не использовал заведомо
старое распределение. Допуск для вставленных и обновленных строк равен порогу
`fasttrun.stats_refresh_threshold`, умноженному на `1 - d`, где `d` - доля
различных значений среди строк, но не меньше меньшего из порога и 5%. Колонка с
немногими значениями получает почти весь порог, почти уникальная - не больше
5%: вставка или обновление может сосредоточить строки на одном значении, и
"редкое" значение станет частым. Удаление так сделать не может, доля любого
оставшегося значения вырастет не больше чем в `1 / (1 - доля удаленных)` раз,
поэтому удаленные строки сравниваются с самим порогом. Изменения складываются
через `COMMIT`, поэтому несколько небольших транзакций подряд гасят статистику,
как одна. Запись, которая идет мимо исполнителя и `COPY`, в журнал транзакции не
попадает, ограничение описано в [ограничениях](limitations.md).

`track_counts=on` требуется для проверки свежести статистики столбцов и
быстрого дельта-пути. При `off` fasttrun продолжает обновлять размер таблицы
через сканирование или выборку блоков, но не сохраняет и не публикует локальную
статистику столбцов. При попытке собрать статистику непустой таблицы расширение
один раз за время жизни backend пишет `WARNING`. После включения `track_counts` снова вызовите
`fasttrun_analyze()` или `fasttrun_collect_stats()`.

Если сбор не отключен через `sample_rows=0` и не остановлен лимитом памяти,
явный `fasttrun_collect_stats()` запускает полный проход по таблице. Ограничение
`fasttrun.max_analyze_pages` относится к сканированиям внутри
`fasttrun_analyze()` и не ограничивает этот явный вызов. Так явный вызов
строит статистику колонок по точному счету строк и выборке из всей кучи там,
где выборке блоков нельзя доверять: значения сгруппированы по страницам, или
после массового `DELETE` куча стала разреженной, и выборка может не попасть ни
в один живой блок. Размер таблицы для планировщика он не публикует, это делает
`fasttrun_analyze()`. Цена - полный проход таблицы при каждом таком вызове.

Обычный полный `ANALYZE` возвращает управление статистикой ядру PostgreSQL для
всей таблицы. `ANALYZE table (col1, ...)` передает ядру только перечисленные
столбцы, а локальная статистика остальных столбцов сохраняется. `VACUUM` без
`ANALYZE` статистику столбцов не меняет. `VACUUM FULL`, `CLUSTER` и смена типа
колонки переписывают таблицу и скрывают старую локальную статистику до
следующего сбора.

DDL, которое не меняет строки и смысл оставшихся колонок, статистику колонок
сохраняет, как ядро сохраняет `pg_statistic`: `CREATE INDEX` и `ALTER TABLE` с
параметрами хранения, `ADD COLUMN`, `DROP COLUMN`, ограничениями, значениями по
умолчанию, `NOT NULL`, целями статистики и триггерами. `DROP COLUMN` убирает
статистику только своей колонки. `ADD COLUMN` с выражением `GENERATED ...
STORED` или с изменчивым значением по умолчанию переписывает таблицу теми же
строками, и статистика переходит на новый файл. После построения индекса, в том числе для
`UNIQUE` или `PRIMARY KEY` внутри `ADD COLUMN`, число строк и страниц берется у
ядра: оно только что посчитало их точно, а остальные индексы сохраняют свои.
`REINDEX` нового индекса не строит: таблица сохраняет свои числа до следующего
analyze, как и без `REINDEX`. Смена типа колонки и прочие
`ALTER TABLE` скрывают статистику таблицы до следующего сбора.

### Выражения индексов

Статистику выражений индексов fasttrun собирает из той же выборки строк, как
ядерный `ANALYZE` в `compute_index_stats`: каждое выражение вычисляется по
выбранным строкам и анализируется как столбец своего типа. Планировщик
получает ее по oid индекса, свежесть проверяется по счетчикам таблицы, как у
ее столбцов, а `UPDATE` засчитывается выражению всегда: оно может читать любую
колонку. Выражения вычисляются от имени владельца таблицы в ограниченном
контексте безопасности, как в `ANALYZE`. Выражения частичных индексов остаются
на оценках по умолчанию: строки такого индекса - лишь часть таблицы, и
статистику всей таблицы планировщик из него не берет. При
`fasttrun.sample_rows = -1` размер выборки учитывает и цели выражений. При
`fasttrun.use_typanalyze = off` выражения не собираются. `DROP INDEX` убирает
статистику выражений своего индекса.

### Расширенная статистика

Объекты `CREATE STATISTICS` строит только ядерный `ANALYZE`, в
`pg_statistic_ext_data`, и хука для них у планировщика нет. Если у таблицы есть
такой объект, `fasttrun_analyze()` и `fasttrun_analyze_bulk()` выполняют для нее
обычный `ANALYZE`, и планировщик получает статистику ядра, многоколоночные
оценки в том числе. Цена - запись каталога и общие сообщения инвалидации, как у
любого `ANALYZE`, и выборка ядра, обычно больше выборки fasttrun. Счетчик
`analyze_core_handoff` в `fasttrun_counters()` считает такие вызовы. Ядро пропускает таблицу, которую вызывающий не вправе
анализировать, поэтому передача идет только тем, кого пустит ядро: на PG16
владельцу таблицы или базы, на PG17 и позже владельцу базы и обладателю права
`MAINTAIN` (у владельца таблицы оно есть, пока он сам его не отозвал). Остальным
fasttrun собирает
статистику столбцов сам, а объекты расширенной статистики остаются от
последнего обычного `ANALYZE` и описывают прошлое заполнение. Планировщик их
тогда не берет и считает многоколоночные оценки по свежей статистике столбцов,
пока обычный `ANALYZE` не построит заново все объекты: строки их данных
сравниваются до и после команды. Явный
`fasttrun_collect_stats()` собирает и для такой таблицы локальную статистику
столбцов, и объекты так же перестают действовать до обычного `ANALYZE`.

## Настройки

Контекст "пользователь" означает, что параметр можно менять через `SET`.
Контекст "администратор" означает superuser-контекст или отдельно выданное
право `SET ON PARAMETER`. Для изменения этих GUC рестарт не нужен.

### Основные параметры

| Параметр | По умолчанию | Диапазон | Контекст | Назначение |
|---|---:|---:|---|---|
| `fasttrun.auto_collect_stats` | `on` | boolean | пользователь | Собирать статистику столбцов внутри `fasttrun_analyze()` |
| `fasttrun.sample_rows` | `3000` | `-1..1000000` | пользователь | `0` отключает сбор столбцов. При `use_typanalyze=on` значение `-1` использует размер выборки, запрошенный PostgreSQL, а при `off` - 3000 строк |
| `fasttrun.stats_refresh_threshold` | `0.2` | `0..1` | пользователь | Допуск, до которого планировщик пользуется статистикой столбцов между DML и следующим analyze: для вставленных и обновленных строк - с поправкой на долю различных значений, для удаленных - сам порог. Пересбор не регулирует: analyze пересобирает после любого DML. `0` скрывает статистику после любого DML |
| `fasttrun.invalidate_threshold` | `0.2` | `0..1` | пользователь | Допустимое накопленное изменение размера таблицы и ее индексов до локального сброса планов |
| `fasttrun.use_typanalyze` | `on` | boolean | пользователь | Использовать ядерные обработчики статистики. `off` оставляет только базовые показатели |
| `fasttrun.zero_sinval_truncate` | `on` | boolean | пользователь | `on` очищает файлы без общих сообщений, а `off` использует ядерный путь очистки |
| `fasttrun.max_analyze_pages` | `100000` | `0..2147483647` страниц | пользователь | Выше порога первый проход `fasttrun_analyze()` переходит к выборке блоков. Пересбор после изменений при точном счете от порога не зависит и выбирает блоки, если таблица больше цели выборки. `0` требует полный проход везде |
| `fasttrun.max_stats_memory` | `0` | КБ | пользователь | Мягкий предел памяти статистики столбцов. `0` означает отсутствие предела |
| `fasttrun.template_stattarget` | `on` | boolean | пользователь | Брать цель статистики колонки у одноименного шаблона в `fasttrun.prewarm_schema`, если у временной таблицы она не задана |
| `fasttrun.log_min_duration` | `-1` | мс | суперпользователь | Писать в журнал сервера вызовы `fasttruncate()` и `fasttrun_analyze()` не короче порога: таблицу, время, путь вызова, опубликованные страницы и строки. `-1` выключает журнал, `0` пишет каждый вызов |

При размере страницы 8 КБ значение `max_analyze_pages=100000` соответствует
примерно 800 МБ heap.

Оставляйте `fasttrun.zero_sinval_truncate=on` в рабочей среде. Значение `off`
предназначено для диагностики и проверки совместимости. Оно не делает очистку
более безопасной и возвращает общие сообщения инвалидации. Ошибка внутри
ядерного критического участка в этом режиме может привести к `PANIC` и
завершению всех серверных сеансов экземпляра PostgreSQL. Автоматический
перезапуск процессов после этого зависит от `restart_after_crash`.

`max_stats_memory` проверяется только перед первым сбором статистики для новой
таблицы. Уже сохраненная статистика продолжает обновляться. Равенство текущего
размера пределу разрешено, поэтому первая новая таблица может превысить лимит
на полный объем статистики всех своих столбцов. Размер этого превышения заранее
не ограничен. В предел входит только `column_stats_bytes`, а память
`analyze_bytes` не учитывается. Автоматического вытеснения и LRU нет. Если лимит
остановил автоматический сбор, backend выдает `WARNING` один раз. Явный
`fasttrun_collect_stats()` выдает `NOTICE` при каждой такой попытке.

Параметры учета и предварительного создания описаны в
[tracking.md](tracking.md#параметры).

## Цена пересбора

Замер на PG16, выборка 3000 строк, время одного `fasttrun_analyze()`:

| Таблица | Без изменений | Дельта без пересбора | После DML, с пересбором |
|---|---:|---:|---:|
| 7 столбцов, 1 тыс. строк | ~0,001 мс | 0,008 мс | 0,72 мс |
| 23 столбца, 10 тыс. строк | ~0,001 мс | 0,007 мс | 7,8 мс |
| 100 столбцов, 100 тыс. строк | ~0,001 мс | 0,3 мс | 43 мс |

Вызов без изменений от размера кеша не зависит. Дельта без пересбора - это
цена при `fasttrun.auto_collect_stats = off`. Пересбор растет с числом
столбцов и размером выборки, а не с размером таблицы: строки выбираются из
случайных блоков. Каждый пересбор сбрасывает сохраненные планы таблицы в этом
backend, остальные backend он не трогает.

## Память

Кеши статистики принадлежат физическому backend и не разделяются между
соединениями. Таблица из 7 столбцов с двумя текстовыми при
`default_statistics_target = 100` занимает около 29 КБ, 700 таких таблиц - около
20 МБ. При 300 таблицах по 300 столбцов объем может составлять десятки или
сотни мегабайт на backend. Широкие значения и увеличенный
`default_statistics_target` повышают расход.

Для измерения используйте фактические данные:

```sql
SELECT pg_backend_pid(), *
FROM fasttrun_cache_stats();
```

Запрос показывает только backend, на котором он выполнен. В transaction
pooling разные вызовы могут попасть на разные серверные соединения.

Периодический ресайкл соединений освобождает локальные кеши. Для предсказуемой
деградации можно задать `fasttrun.max_stats_memory`. После достижения лимита
новые таблицы продолжат получать оценки размера, но останутся без локальной
статистики столбцов. Уже принятая статистика не вытесняется.
