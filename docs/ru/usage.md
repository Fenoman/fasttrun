# Использование

> English version: [usage.md](../en/usage.md). Обзор расширения - в [README](../../README.md).

## Основной рабочий цикл

Очищайте таблицу перед началом нового расчета. Не полагайтесь только на очистку
в конце: клиент может завершиться с ошибкой до последнего шага.

### Шаблон для обычного SQL

Это пример рабочего порядка, а не готовый запрос: замените `source_data` и
последующий `SELECT` объектами своего приложения.

```sql
BEGIN;

CREATE TEMP TABLE IF NOT EXISTS temp_work (
    id bigint,
    value numeric
);

-- Удаляем данные, оставшиеся от предыдущего использования backend.
SELECT fasttruncate('pg_temp.temp_work');

INSERT INTO temp_work
SELECT id, amount
FROM source_data
WHERE processing_date = CURRENT_DATE;

-- Обязательно после каждого повторного заполнения.
SELECT fasttrun_analyze('pg_temp.temp_work');

SELECT ...
FROM temp_work
JOIN ...;

COMMIT;
```

`ROLLBACK` отменит обычные изменения транзакции, но не вернет данные, которые
уже были удалены успешным `fasttruncate()`.

### Шаблон для PL/pgSQL

Внутри PL/pgSQL функции с результатом `void` вызываются через `PERFORM`:

```sql
DO $plpgsql$
BEGIN
    CREATE TEMP TABLE IF NOT EXISTS temp_work (
        id bigint,
        value numeric
    );

    PERFORM fasttruncate('pg_temp.temp_work');

    INSERT INTO temp_work
    SELECT id, amount
    FROM source_data
    WHERE processing_date = CURRENT_DATE;

    PERFORM fasttrun_analyze('pg_temp.temp_work');

    -- Дальнейшие запросы к temp_work.
END;
$plpgsql$;
```

`PERFORM` нельзя выполнять как отдельную команду в `psql`. В обычном SQL
используйте `SELECT fasttruncate(...)` и `SELECT fasttrun_analyze(...)`.

Пример более сложной `create_temp_table()` лежит в
[examples/create_temp_table.sql](../../examples/create_temp_table.sql). Это пример
интеграции, а не часть API расширения. Он зависит от `pg_variables`, схемы
шаблонов и роли `_client`. В нем текстовые имена подставляются в динамический
SQL без `%I`, поэтому не передавайте в него недоверенные значения и перед
внедрением в рабочую среду адаптируйте функцию под свой проект.

`CREATE TEMP TABLE IF NOT EXISTS` не обновляет структуру уже существующей
таблицы. При изменении шаблона после деплоя проверяйте версию структуры и при
необходимости удаляйте и создавайте таблицу заново.

## Работа через пулер

Временная таблица принадлежит физическому серверному процессу PostgreSQL, а не
логическому клиенту пулера. Следующий клиент может получить backend, в котором
остались таблицы и данные предыдущего клиента.

Соблюдайте следующие правила:

1. Очищайте рабочую таблицу в начале каждого расчета.
2. После заполнения всегда вызывайте `fasttrun_analyze()`.
3. В transaction pooling выполняйте весь цикл в одной явной транзакции.
4. Statement pooling для такого цикла не подходит.
5. Не считайте fasttrun границей безопасности между клиентами. Очистка при
   передаче backend должна обеспечиваться приложением или настройкой пулера.
6. После `SQLSTATE 55000` backend нельзя возвращать в пул, пока таблица не
   восстановлена. Проверить это можно после завершения транзакции запросом к
   `fasttrun_blocked_tables()`: пустой результат означает, что блокировок нет.
   Если результат восстановления неочевиден, закройте физическое соединение и
   позвольте пулеру создать новое.
7. `DISCARD TEMP` и `DISCARD ALL` удаляют временные таблицы. Это безопасно,
   но устраняет выгоду от их повторного использования.

При `SQLSTATE 55000` сразу перейдите к разделу
["Восстановление после ошибки"](#восстановление-после-ошибки).

Учет и предварительное создание - отдельная необязательная возможность.
`fasttrun_prewarm()` имеет смысл вызывать при создании нового физического
соединения, а не при каждой выдаче соединения клиенту.

## Режим передачи ядру

`fasttrun.passthrough = on` выключает собственную работу расширения, не меняя
вызывающий код: `fasttruncate()` выполняет `TRUNCATE ONLY`, а
`fasttrun_analyze()`, `fasttrun_analyze_bulk()` и `fasttrun_collect_stats()` -
`ANALYZE`. Хуки и кеши сеанса бездействуют, функции диагностики показывают
пустые кеши. Проверки входа прежние: отсутствующая таблица - тихий выход,
постоянная или секционированная - ошибка.

Режим служит аварийным выключателем: если на конкретной сборке сервера
расширение мешает, его выключают настройкой, а не правкой прикладного кода.
Значение берется при подключении и не меняется до конца сеанса. Задает его
суперпользователь в `postgresql.conf` (действует для сеансов, открытых после
перечитывания конфигурации), через `ALTER ROLE ... SET`, `ALTER DATABASE ...
SET` или в параметрах подключения.

Цена режима - работа ядра. В PostgreSQL и PostgresPro обычные `TRUNCATE` и
`ANALYZE` временной таблицы меняют строки каталога и рассылают общие сообщения
инвалидации всем процессам кластера. Tantor SE 18.6.x оставляет сообщения о
`TRUNCATE` и `ANALYZE` временной таблицы внутри своего процесса и в общую
очередь их не пишет, при `enable_temp_memory_catalog` и `on`, и `off` (замер на
18.6.3 по счетчику общей очереди: 0 сообщений на 10 вызовов каждой команды).
Там цена режима - запись строк каталога при `enable_temp_memory_catalog = off` и
полный `ANALYZE` вместо пересчета по дельте. `fasttruncate()` и
`fasttrun_analyze()` в обычном режиме не рассылают ни одного сообщения.

## Функции

Публичный API содержит 14 SQL-функций.

### Основные операции

| Функция | Назначение | Общие сообщения инвалидации |
|---|---|---|
| `fasttruncate(text)` | Очищает одну локальную временную heap-таблицу, ее индексы, TOAST и индексы TOAST | Нет при `zero_sinval_truncate=on`, а при `off` отправляется служебное сообщение для каждого очищенного отношения |
| `fasttrun_analyze(text)` | Обновляет локальные оценки размера и при необходимости статистику столбцов | Нет, кроме таблиц с объектами `CREATE STATISTICS`: их обрабатывает обычный `ANALYZE` |
| `fasttrun_analyze_bulk(VARIADIC text[])` | Последовательно выполняет `fasttrun_analyze` для массива таблиц | Как у `fasttrun_analyze` |
| `fasttrun_collect_stats(text)` | Явно пересобирает локальную статистику столбцов | Нет |

`fasttruncate()` берет `ExclusiveLock` на таблицу, ее индексы и TOAST.
Читать временную таблицу другой сеанс не может, а `AccessExclusiveLock` на
отношение ядро пишет в WAL для реплик и ради этой записи назначает транзакции
номер. Поэтому `fasttruncate()` не назначает транзакции номер и не пишет WAL ни
на быстром пути, ни при очистке файлов: хранилище временных отношений в WAL не
попадает. `fasttrun_analyze()` и `fasttrun_collect_stats()` берут
`AccessShareLock` на время работы. Открытый курсор или активный запрос к
очищаемой таблице приведет к обычной SQL-ошибке до изменения файлов.

Цена очистки растет с числом отношений набора и с `temp_buffers`: для каждого
отношения ядро просматривает весь массив локальных буферов, так же как при
ядерном `TRUNCATE`.

Если таблица и TOAST физически пусты, а локальная статистика таблицы и
индексов уже соответствует этому состоянию, повторный `fasttruncate()`
пропускает файловую очистку, перестроение индексов и инвалидацию планов.
Проверки активных обращений сохраняются. Несовпадение локаторов, размеров,
статистики или счетчиков DML, а также незавершенная очистка возвращают
вызов на полный путь. Одного `reltuples = 0` для пропуска недостаточно.
Если `COMMIT` не смог перенести базу счетчиков (счетчики недоступны), быстрый
путь восстанавливает ее для следующего заполнения и `fasttrun_analyze()`. Если
пустое состояние еще не согласовано с сохраненными планами, выполняется полная
очистка с инвалидацией.

Для этих функций `NULL` и отсутствующая таблица означают пустую операцию.
`fasttrun_analyze_bulk()` также пропускает `NULL`-элементы массива. Если
найдена обычная таблица, неподдерживаемый метод хранения, секционированный
родитель или родитель наследования, функция завершится ошибкой.

Пакетный вызов не объединяет локальные инвалидации планов. Они выполняются
только для отношений, где статистика действительно изменилась. В худшем случае
для N таблиц будет N полных проходов по локальному списку планов.

### Диагностика

| Функция | Назначение |
|---|---|
| `fasttrun_relstats(text)` | Возвращает текущие локальные `relpages` и `reltuples` |
| `fasttrun_inspect_stats(text)` | Показывает сохраненные кандидаты статистики в формате `pg_statistic`. У строки выражения индекса `starelid` - oid индекса, а `staattnum` - номер колонки индекса |
| `fasttrun_cache_stats()` | Показывает количество записей и память локальных кешей |
| `fasttrun_cached_tables()` | Перечисляет отношения, для которых сеанс хранит оценки и статистику |
| `fasttrun_blocked_tables()` | Перечисляет таблицы, заблокированные в сеансе после незавершенной очистки |
| `fasttrun_counters()` | Возвращает счетчики событий расширения |
| `fasttrun_counters_reset()` | Обнуляет счетчики событий |

Для отсутствующей таблицы `fasttrun_relstats()` возвращает `NULL`, а
`fasttrun_inspect_stats()` - пустой набор. Пустой набор также означает, что
локальная статистика столбцов еще не собиралась.

`fasttrun_inspect_stats()` предназначена для диагностики. Наличие строки в ее
результате не гарантирует, что планировщик использует эту статистику прямо
сейчас: проверка свежести может временно скрыть ее.

`fasttrun_cache_stats()` всегда возвращает одну строку со следующими полями:

- `analyze_entries`
- `column_stats_relid_entries`
- `column_stats_entries`
- `analyze_bytes`
- `column_stats_bytes`
- `total_bytes`

`total_bytes` равен сумме `analyze_bytes` и `column_stats_bytes`. Все значения
относятся только к текущему физическому backend.

`fasttrun_cached_tables()` возвращает строку на каждое отношение, которое
знает текущий backend. Он открывает каждое отношение и читает его размер, на
700 таблицах это 70-100 мс: для периодического мониторинга подходит, для
проверки при каждой выдаче соединения пулером - нет. Поля результата:

| Поле | Значение |
|---|---|
| `relid`, `relname` | Отношение. `relname` пустое, если отношение уже удалено |
| `kind` | `table` или `index` |
| `relpages`, `reltuples` | Опубликованная оценка размера |
| `count_exact` | Число строк получено полным проходом или точной дельтой, а не выборкой блоков. У индекса пусто |
| `delta_state` | Следующий `fasttrun_analyze()` посчитает строки по счетчикам, без прохода по таблице. У индекса пусто |
| `column_stats` | Число колонок и выражений индексов с сохраненной выборкой |
| `hidden_columns` | Сколько из них проверка свежести сейчас скрывает от планировщика |

`fasttrun_blocked_tables()` возвращает `relid` и `relname` таблиц, которые
после ошибки `fasttruncate()` заблокированы в текущем backend. Проверяйте его
после завершения транзакции: внутри нее `DROP` прячет таблицу, а откат
возвращает ее вместе с блокировкой. Пустой результат вне транзакции означает,
что соединение можно возвращать в пул.

`fasttrun_counters()` возвращает строки `counter`, `value`, `scope`. При
`shared_preload_libraries` значения общие для экземпляра (`scope = cluster`):
каждый backend добавляет свои события в свой участок общей памяти в конце
каждой транзакции, а функция суммирует участки. Без предзагрузки значения относятся к текущему backend
(`scope = backend`). Через пулер в режиме транзакций полезен только первый
вариант. Счетчики начинаются с нуля после запуска сервера и после
`fasttrun_counters_reset()`. Сброс обнуляет общие значения и события
вызвавшего backend. События другого backend из транзакции, открытой во время
сброса, попадут в сумму при ее завершении.

| Счетчик | Что считает |
|---|---|
| `truncate_calls` | Вызовы `fasttruncate()` для существующей временной таблицы |
| `truncate_empty_fast_path` | Из них вызовы, где таблица уже была пустой и работа с файлами не понадобилась |
| `truncate_failed_after_change` | Ошибки после начала изменения файлов, то есть новые блокировки |
| `analyze_calls` | Вызовы `fasttrun_analyze()`, в том числе из `fasttrun_analyze_bulk()` |
| `analyze_noop` | Вызовы без изменений с прошлого вызова |
| `analyze_delta` | Вызовы, которые посчитали строки по счетчикам изменений |
| `analyze_cold_scan` | Полные проходы по таблице |
| `analyze_cold_block_sample` | Проходы выборкой блоков по таблице больше `fasttrun.max_analyze_pages` |
| `analyze_core_handoff` | Вызовы, переданные обычному `ANALYZE`, потому что у таблицы есть объекты `CREATE STATISTICS` |
| `storage_found_empty` | Таблицы, найденные пустыми мимо счетчиков, например после `ON COMMIT DELETE ROWS` |
| `column_collects` | Сборы статистики колонок |
| `column_collects_during_write` | Сборы, сделанные во время записи таблицы: их выборка планировщику не отдается |
| `refresh_deferred` | Пересборы, отложенные из-за идущей записи |
| `partial_index_rescans` | Вызовы `fasttrun_analyze()`, которые пересчитали частичные индексы таблицы |
| `plan_invalidations` | Локальные сбросы сохраненных планов |
| `stats_served` | Запросы планировщика, получившие сохраненную статистику колонки |
| `stats_hidden` | Запросы планировщика, получившие оценки по умолчанию вместо статистики колонки, которую ведет fasttrun: выборка устарела, собрана во время записи или сброшена очисткой либо `COMMIT` |
| `writer_registry_overflows` | Переполнения реестра пишущих операторов |
| `commit_carried` | Таблицы, чьи счетчики `COMMIT` перенес в следующую транзакцию |
| `tracking_rejected` | Имена, которые не поместились в реестр учета `CREATE TEMP TABLE` |

`fasttrun.log_min_duration` пишет в журнал сервера отдельные медленные вызовы
`fasttruncate()` и `fasttrun_analyze()` с путем, которым шел вызов.

Функции учета и предварительного создания таблиц описаны в
[tracking.md](tracking.md#функции).

## Восстановление после ошибки

### Ошибка до изменения файлов

Если ошибка произошла до начала физической очистки, PostgreSQL откатывает
операцию обычным способом и прежние данные остаются целы.

### SQLSTATE 55000

Если ошибка возникла после начала очистки, прежние файлы уже нельзя безопасно
восстановить. fasttrun блокирует таблицу в текущем backend. `SELECT`, DML,
`COPY`, планирование и функции расширения для нее возвращают `SQLSTATE 55000`, в
том числе запрос, который читает ее через встроенную SQL-функцию или через
родителя наследования, запись через секционированного родителя и план,
построенный до сбоя, например следующий оператор SQL-функции. Обычный
`ROLLBACK`, откат к точке сохранения и `TRUNCATE` через родителя наследования,
который потом откатился, блокировку не снимают, пока сама таблица существует.
Если откатывается создание таблицы, расширение удаляет ее запись незавершенной
операции вместе с локальными кешами. Это действует и при первом вызове fasttrun
во вложенном блоке.

Сначала завершите ошибочную транзакцию:

```sql
ROLLBACK;
```

Затем выберите один способ восстановления:

1. Повторите `fasttruncate()`. После успешного вызова таблица снова доступна,
   пуста и должна быть заполнена заново.
2. Удалите таблицу и создайте ее заново.
3. Выполните `DISCARD TEMP` или `DISCARD ALL` вне транзакции. Это удалит все
   временные таблицы текущего backend.
4. Закройте физическое соединение. Для backend под управлением пулера это
   самый простой безопасный вариант.

Пример повторной очистки:

```sql
BEGIN;
SELECT fasttruncate('pg_temp.temp_work');
COMMIT;
```

`DISCARD ALL` дополнительно сбрасывает подготовленные планы, параметры сессии и
другое состояние соединения. Если нужно удалить только временные таблицы,
используйте `DISCARD TEMP`.

Для новых операций приложение можно временно вернуть к штатным командам:

```sql
TRUNCATE pg_temp.temp_work;
ANALYZE pg_temp.temp_work;
```

Это не восстанавливает уже заблокированную fasttrun таблицу. Для нее используйте
один из четырех способов выше.

### Ошибка в запасном режиме

При `fasttrun.zero_sinval_truncate=off` расширение вызывает ядерный
`RelationTruncate` для каждого отношения. Ошибка в критическом участке
физической очистки PostgreSQL приводит к `PANIC`. Это завершает все серверные
сеансы данного экземпляра, а не только текущий backend. При
`restart_after_crash=on` postmaster заново запускает процессы и выполняет
аварийное восстановление. Пулер увидит массовый обрыв соединений.

При `restart_after_crash=off` PostgreSQL не запускает процессы автоматически.
Перезапуск и восстановление должен выполнить оператор или система управления
кластером.

Проверьте журнал и состояние всего экземпляра PostgreSQL. Продолжать работу
старых соединений после такого события невозможно.
